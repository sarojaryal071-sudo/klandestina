# Klandestina — Website

Plain HTML/CSS/JS site for Klandestina Cantina, Helsinki. No build step, no framework — open `index.html` in a browser (or serve the folder) and it runs.

## Hero photo

The hero is a full-bleed real photo of the restaurant (the neon sign and open kitchen window) with a navy overlay and the headline/buttons over it — not the old photo-less radial-gradient-over-`--bg` treatment. Two source photos (desktop 16:9, mobile 9:16 — both already shot/cropped at those exact aspect ratios, confirmed by measuring them: 1672×940 and 940×1672, both within a fraction of a percent of 16:9/9:16) live untouched at `images/hero/hero-desktop-source.png` / `hero-mobile-source.png`; never recoloured, cropped, or restyled — every other file under `images/hero/` is generated from them. Desktop and mobile (≤768px) are genuinely different layouts, not just a resized version of the same composition — see "Mobile: cinematic poster layout" below for the second one.

**Generating the responsive variants (`scripts/build-hero.mjs`).** AVIF + WebP + JPG at several widths each (`npm i --no-save sharp && node scripts/build-hero.mjs`, same one-off/manual-run shape as `scripts/build-gallery.mjs`, just not wired into a GitHub Action since there's only ever two source photos and they don't change on their own). Desktop is a straight resize of the full photo. Mobile is **extracted** (`sharp(...).extract({...})`, a read-time crop — the source file itself is never touched) before resizing: `left: 121, top: 560, width: 556, height: 1112` out of the 940×1672 source. See "Mobile: cinematic poster layout" below for why a crop, not just `object-position`, is what the new mobile design actually needs. **The task asked for desktop widths 1280/1920/2560 and mobile 720/1080/1440 — the desktop source (1672px) and, more so, the mobile CROP (556px, since cropping is itself a resolution cut) are both smaller than their largest requested width**, so any requested width above what's actually available is dropped and that ceiling is generated instead (`widthsToGenerate()` in the script): desktop ships 1280/1672w, mobile ships 375/556w (375 is an extra smaller tier added on top of the requested numbers, since none of 720/1080/1440 would otherwise fit under the crop's 556px ceiling and mobile would otherwise ship only one size). Upscaling past the real available resolution would invent detail that isn't there, which is exactly what "do not ... restyle the images themselves" rules out — flagging this here since it's a real deviation from the literal requested numbers, not a silent one. Quality ~72-75 per format; checked for banding in the flat dark-wall region specifically (mozjpeg/normal JPEG is the format most prone to it) by counting distinct luminance levels in that band — a smooth ramp, not a handful of flat posterized steps, on both the desktop resize and the mobile crop. All fourteen files together are well under 1MB.

**Markup (`index.html`'s `<picture>`).** Mobile `<source>`s match `(max-width: 768px)` — the exact breakpoint `.hero`'s own mobile CSS switches on below, so the photo and the text layout always agree on which "mode" the hero is in (this is the site's *hero-specific* breakpoint, not its general 900px mobile-topbar/nav breakpoint — see "Assumptions" at the bottom for what that means for the 769-900px gap). AVIF and WebP sources before a plain `<img>` JPG fallback with its own `srcset`/`sizes`; no `loading="lazy"` (it's the hero, always above the fold), `fetchpriority="high"`, real `alt` text (not `alt=""` — this depicts the actual signage, not decorative filler) that follows the EN/FI switch via a `data-i18n-alt` hook (`script.js`'s `applyTranslations()`, mirroring the existing `data-i18n-aria-label` one; `scripts/prerender.mjs`'s `translateStaticAlt()` does the equivalent swap for the static `fi/index.html`). Two `<head>` preloads (one per breakpoint, `type="image/avif"` so a browser that can't decode AVIF just skips the preload rather than fetching a format it won't use — it still gets the photo normally via the `<picture>` fallback cascade, just without the early-fetch boost) target exactly the same sources the matching `<source>` would pick.

**Desktop object position.** The source's own bright signage/window band was located by sampling actual pixel brightness per column/row (not eyeballed): columns 50-80%, rows 29-79% of the frame. `object-position: 65% 50%` keeps that band on screen under `object-fit: cover`'s own crop math — checked by calculation (not just by looking) against every required breakpoint (1280×720, 1440×900, 1920×1080, plus deliberately extreme ultrawide/short-window cases) using `cover`'s actual scale formula (`scale = max(viewportW/imageW, viewportH/imageH)`, crop removed symmetrically around the `object-position` point) — the sign never gets cropped out at any of them.

**Mobile: cinematic poster layout (≤768px).** A second, deliberately different mobile design: the photo anchored to the top (`object-position: center top`) with the sign/window in the upper portion of the screen, and ONE text block — eyebrow, headline, subline, the two buttons in a row — pinned to the bottom, instead of the earlier split top/bottom layout.

- **Why the mobile image is a crop, not just `object-position`.** `object-fit: cover` on a tall, narrow viewport (which every phone is, relative to this 9:16 photo) is *height-bound* — the browser always shows the image's *full height*, cropping left/right, never top/bottom. That means `object-position`'s vertical value has **no effect at all** here: the sign/window's position as a fraction of the screen is fixed by where it sits as a fraction of the *source photo's own height*, regardless of what `object-position` says. Measured directly: the full photo's sign/window band spans roughly rows 32-82% of its own height — nowhere near the top. The only way to actually move it up is to crop the source first, so the band becomes a different (smaller) fraction of what's displayed. The crop (`left: 121, top: 560, width: 556, height: 1112`, see `build-hero.mjs`) starts close to the sign's own top edge (small headroom) and keeps everything below it down to the source's own bottom edge — maximizing how much "fade zone" the crop gets out of the limited vertical content that actually exists below the window in the source. Confirmed by rendering the crop and sampling its own pixel rows: the sign/window band now ends around 60-65% of the crop's height, with the rest reading progressively calmer/darker toward the bottom.
- **Overlay.** Two `linear-gradient`s on `.hero-overlay`: a short one (~15%) behind the fixed topbar at the very top, and a longer one fading the lower portion of the photo into solid `var(--bg)` — starting ~38% from the bottom (~62% from top, chosen to land just past where the crop's own sign/window band ends) and reaching fully solid by the very bottom, where the text block actually sits. The fade isn't a straight ramp: it's front-loaded (most of the opacity gained by 78% from the top, not spread evenly to 100%) — found by actually rendering text at its real position and sampling the pixels behind it, not just by the math above. A straight linear fade left a bright metal-counter reflection showing through right where the eyebrow sits, at ~3.8:1 contrast for the `--accent` eyebrow text — under the 4.5:1 AA floor. The front-loaded curve (same start point, so it still clears the sign/window) fixed it: re-measured worst-case (95th-percentile-brightest pixel behind the text, not just the average) contrast across all four required widths is ≥4.64:1 for the eyebrow and comfortably higher everywhere else.
- **One row of equal-width buttons.** `#hero-buttons` becomes a flex row (`gap: 12px`) with each `.btn` at `flex: 1 1 0`, `height: 52px`, `border-radius: 10px`, `font-size: 15px` (all per the task's own spec) and `padding: 0 6px` + `letter-spacing: normal` — both tightened specifically to make the real EN/FI label text actually fit without truncating at 320px *at that exact 15px font size* (checked via real rendered `scrollWidth` vs `clientWidth`, not estimated): "Reserve a Table"/"See the Menu" and "Varaa pöytä"/"Katso ruokalista" all fit with zero pixels to spare at 320px once both tweaks were in. `text-overflow: ellipsis` stays on as a safety net for a future longer label, not as the primary plan.
- **No scroll cue.** The earlier split-layout's bottom scroll-cue icon is gone entirely (not just hidden) — this layout's whole bottom band is the text block, and the task's own instruction is explicit that the space is needed for it instead.
- **A `min-height: 600px` floor bug, found and fixed.** Writing `min-height: 600px;` after the base rule's `min-height: 100svh;` *replaced* it rather than acting as a floor on top of it (same CSS property — the later declaration wins outright, it doesn't combine as "whichever is larger"). The practical effect: on an 812px-tall viewport, the hero rendered at a flat 600px, squeezing the next section into view and pushing the text block's measured position (and the contrast numbers above) to the wrong place entirely. Fixed with `min-height: max(600px, 100svh);` (with a plain `100vh` fallback written first, same pattern as everywhere else in this file that uses `svh`) — now the hero is `max(600px, 100svh)` as actually intended. One real consequence of the literal 600px floor remains, deliberately: on the shortest required test size (320×568, an 568px viewport), the hero is still 600px tall (the floor), so the button row's last ~8px sits just past the fold — a tiny scroll, not a cut-off; reducing the floor wasn't requested and doing so on my own would mean second-guessing an explicit number.
- **≤2-line headline/subline, subline hidden below 360px.** `-webkit-line-clamp: 2` on both as a hard cap (not just a hint) in case a future rewrite of either string runs long; the subline is dropped entirely (not shrunk further) below 360px via its own `@media (max-width: 359px)` rule, per the task's own explicit fallback list.

**Social image.** See "SEO" below — `images/og/og.jpg` is now a crop of the desktop hero photo, not a generated logo-on-gradient graphic.

**Assumptions / deviations from the literal task text:**
- Desktop widths above the source's own native resolution (1920/2560) were **not** generated — the largest desktop variant shipped is the source's own native width (1672px). Mobile's three requested widths (720/1080/1440) all exceed the crop's own 556px width and were likewise not generated as-is; mobile ships 375/556w instead (556 being the crop's native ceiling, 375 an extra smaller tier added so there's still more than one size).
- The `<picture>` mobile breakpoint is `(max-width: 768px)`, exactly as the task specifies, and is a *separate* breakpoint from the site's own general 900px one (used for the mobile topbar/hamburger nav, unrelated to the hero). Between 769-900px, the result is the **desktop** hero layout (full landscape photo, left-column text) underneath the **mobile** topbar/hamburger chrome — an intentional consequence of the task's own explicit "768px and down" framing for this layout, not an oversight; checked at 800px wide and it reads fine (see screenshots).
- No zoom/parallax was added (explicitly optional, "skip if it hurts performance") — a continuous `transform` animation on a full-bleed LCP background adds compositing cost during the most performance-sensitive moment of page load, so it was left out in favor of a static image.
- The desktop left-column text width (`min(44vw, 520px)`) is tuned against the three required desktop breakpoints (1280×720/1440×900/1920×1080) plus ultrawide, each verified by calculation to leave real margin before the sign starts — it isn't defended against every conceivable desktop aspect ratio (e.g. a ~901px-wide but very short ~600px-tall browser window, well outside the required test matrix, could theoretically get close); flagging this rather than overbuilding for a case nothing asked for.
- Mobile text alignment is left (matching the desktop column's own alignment) rather than centered — the task offered both as options ("left-aligned (or centred if it looks better at 320px)"); left read better once the button row's own `flex: 1 1 0` stretch already fills the width edge-to-edge regardless.

## Editing the menu

Everything a dish needs — name, price, description, photo — lives in `data/menu.json`. Edit that file and the site updates automatically; no other file needs to change.

The full menu is split into `lunch`, `starters`, `tacos`, `chilaquiles`, `desserts`, `softDrinks`, `beer`, `cocktails`, `wine`, matching the real physical menu boards. `menu.categories` drives the tab row; most tabs map straight to one of those arrays, except `drinks`, which lists `groups: ["softDrinks","beer","cocktails","wine"]` and renders each as its own labeled sub-section in one panel (keeps the tab row to 6 pills instead of 9).

Per-item fields:
- `allergens`: raw letter codes as printed on the menu (`["M","G"]`, `["VEGAN"]`, etc.) — plain display text next to the name, not interactive. **The G/M/L legend itself needs confirming with the owner** — the menu photos show the letters but not what they stand for, so I've stored them as-is without guessing (G/M/L conventionally mean gluten/dairy/lactose-adjacent allergens on European menus, but I didn't want to assert that without the owner's key).
- `price`: usually a string (`"€15"`); `""` for items covered by a category-level price note instead (Lunch's fixed €14.90); or, for wine only, an object `{ glass12, glass16, glass24, bottle }` with `null` for sizes not offered — rendered as a fixed-width 4-column grid (12cl/16cl/24cl/Btl line up in the same columns on every wine row), still plain text.
- `image`: filename inside `images/dishes/`, only set on items that actually have a real dish photo. Omitting it isn't a gap to fill in later — `renderMenuItem()` treats a missing `image` as "this item has no thumbnail" and renders name/description/price full-width with no image area at all, rather than a placeholder square.
- `images`: optional, only meaningful for the click-to-expand detail modal (see "Item detail modal" below) — an array of extra photos for items that have more than one (Quesabirria is the only one right now: `["quesabirria.jpg", "quesabirria-2.jpg"]`). The modal shows `images` when present, falling back to just `[image]` otherwise. `image` alone still drives the thumbnail everywhere else (menu row, dish card) — `images` only ever affects the modal's photo strip.
- `description`: `{ en, fi }`. Cocktail modifiers ("With Mezcal: +2€") and the Amazing Bowl's choose-your-sides/filling text are folded into this as plain prose, not separate interactive fields — nothing on the menu beyond the existing category tabs is clickable.
- A group can carry a standing note above its items via `data/i18n/*.json`'s `menu.notes.<groupId>` (used for Lunch's price/schedule line and Cocktails' "ask about Tequila & Mezcal" line).

## Signature dish carousel

`components/dishCarousel.js` replaced the old setup — a static 3-column grid on desktop, a manually-swipeable flex row on mobile — with one component that behaves identically at every screen size: a single row that auto-scrolls continuously and loops seamlessly, so a visitor sees every dish without tapping anything.

The loop trick: the dish list is rendered twice, back-to-back (`.dish-carousel-set`, `display: contents` so each set groups for `aria-hidden` on the duplicate without breaking the track's flex layout — the individual cards are still the track's direct flex children). A `requestAnimationFrame` loop advances a `translateX` offset and wraps it back to 0 once it passes the width of *one* set; since the second set is pixel-identical to the first, the wrap is invisible. A rAF loop (rather than a CSS `@keyframes` animation) is what makes the optional prev/next arrows possible without a fight: they just nudge the same `offset` value the auto-scroll already owns, so a manual click and the ongoing auto-scroll can never desync. `prefers-reduced-motion: reduce` simply skips starting the loop — the row sits still, and the arrows are still a fully working way to browse it.

**Hairline at the bottom edge of each card.** `.visual` (the card's photo box — `.dish-visual`, `.visual`, and `.tilt-card` are all the same element) is `overflow: hidden` + `border-radius: 22px` with a `background-color` fallback meant to show only before its `<img>` finishes loading. That same element also carries `.tilt-card`'s transitioned `transform` (the hover tilt), and a rounded-corner clip on an element that's also a transform-transition target is a known Chromium compositing edge case: the rasterized layer and its rounded clip mask don't always align pixel-for-pixel, leaving a hairline of whatever's behind the `<img>` visible along one edge (bottom, in practice) even once the photo has fully loaded — invisible to `getBoundingClientRect()` since it's a rasterization artifact, not an actual layout gap. That fallback color is `var(--surface-edge)` (a palette token, not a hardcoded hex), so if the hairline is ever visible it's a tone that belongs to the site's own palette instead of an unrelated color dropped in from outside it. Same fallback-color pattern exists on `.mosaic-tile`/`.gallery-tile` (gallery) — untouched here since neither has a transform-transition on the same element, so they're not exposed to the same compositing case.

Pausing: `pointerenter`/`pointerleave` cover hover on desktop, `pointerdown`/`pointerup` cover a touch press-and-release on mobile — the row pauses whenever either is active and resumes on release. The individual cards drop the `.reveal` scroll-fade-in class they'd normally carry (`renderDishCard()`'s own class is stripped after the fact) — a continuously horizontally-translating element under a scroll-linked reveal animation invited flicker for no real benefit, since these cards don't "enter" the page one at a time the way a vertical list does.

Because `renderSignatureDishes()` calls `renderDishCarousel()` again on every language switch (replacing `#dish-grid`'s contents wholesale), the rAF loop and its `resize` listener both self-terminate the moment their own `track` element is no longer in the document (`if (!document.body.contains(track)) return`) — otherwise every language toggle would leave one more orphaned loop running in the background forever.

## Asymmetric layout, soft-edged photos, and full-bleed imagery

Every section used to center its content in one narrow column — part of why the page felt empty on the sides on wide screens. The Story section (the only one that genuinely pairs a block of text with a single supporting photo — Find Us has a map instead, and the dish carousel/full menu/gallery are inherently symmetric grids/rows, so none of those were forced into this) is now a two-column layout on desktop: text on the left, photo on the right, both vertically centered (`.story-layout`, `flex-direction: row` above 900px). Below 900px it's the same DOM order stacked in a column instead (text, then photo) — no order-reversal trick needed, since "text first" is exactly what both layouts already want. Paragraph/heading text keeps its existing, readable max-width (`.story-body`'s 560px on desktop) rather than stretching edge to edge; asymmetric means text and image occupy different halves, not that text goes full-width.

The photo itself is soft-edged rather than a hard rectangle crop — `.story-photo-img` gets a `mask-image: radial-gradient(ellipse 72% 72% at 50% 50%, black 55%, transparent 100%)` (with the `-webkit-` prefix alongside), fading all four sides into the section's own background instead of a visible boundary line. An ellipse (not a circle) so the fade matches the photo's own 4:5 proportions. There's no dedicated Story photo yet — it reuses one of the `images/dishes/` shots as filler, the same way the gallery already does (see "Known gaps").

Sections without real photography yet (Menu, Visit) get `.section-ambient` instead of a flat background color — the same radial-accent-glow-over-`var(--bg)` technique `.hero` already uses, reused rather than invented fresh. It's isolated in its own class, applied directly on the `<section>` in `index.html`, so dropping it later (once those sections have real photos) is a one-line removal that touches nothing else.

`.container`'s `max-width: 1180px` still caps text exactly as before — that didn't change. What changed is imagery: the dish carousel now sits inside a `.full-bleed` wrapper (`width: 100vw; margin-left/right: calc(50% - 50vw)`, the classic break-out-of-parent-padding trick — robust across breakpoints without tracking each one's padding value; `body`'s existing `overflow-x: hidden` absorbs the sub-pixel rounding it can introduce) so both run closer to the viewport edges on wide screens instead of being boxed in by the section's own 56px side padding.

## Social links

`data/site.json`'s `social` object (`instagram`/`facebook`/`tiktok`, clean profile URLs — no tracking query params) is rendered in the footer by `footer.js` as a row of icon links (`.footer-social`) under the tagline, all `target="_blank" rel="noopener noreferrer"`. The icons are hand-drawn inline SVGs matching the site's own stroke-icon language (the FAB's calendar icon) rather than imported brand assets — same reasoning as the custom CSS map pin instead of a raster logo. This is a new addition, not a rewire: `site.json` already had a (partial, and stale) `social` object, but nothing in the UI had ever rendered it before now.

## Shortcut nav: dims away from the hero

`#shortcut-nav` (`components/nav.js`) is full opacity on the hero, then fades to a low opacity (`.shortcut-nav--dimmed`, `opacity: 0.4`) everywhere past it — still fully clickable throughout, just visually out of the way once a visitor isn't at the very top of the page, restoring to full opacity the moment a cursor or touch actually reaches it (`:hover`/`:focus-within` in `style.css`, so it needs no JS beyond the class toggle). A second, separate `IntersectionObserver` (`observeHero()`, alongside the existing `observeSections()` that tracks which pill lights up as *active*) watches `#hero` specifically and toggles the dimmed class based on `entry.isIntersecting` — deliberately not folded into the active-section observer, since "is the hero still visible at all" and "which section's pill should light up" are different questions with different targets (the active-section list starts at "story", not "hero"). A `0.5s` opacity transition, combined with the observer only firing on actual visibility-threshold crossings rather than every scroll frame, is what keeps this feeling smooth rather than flickery.

The Full Menu section's category tab row (`.tabs`, wrapped in `.tabs-sticky`) is `position: sticky; top: 88px` — pinned just below the nav pill (whose own bottom edge sits around 73px, with the mobile topbar's at 69px, so 88px clears either) while a visitor scrolls through that category's items, then releases back into normal flow once they scroll past the bottom of `.menu-content`. No scroll listener drives this: `.tabs-sticky` is a plain in-flow child of `.menu-content` (section-head, then tabs-sticky, then menu-list), and that's exactly the box CSS's own sticky algorithm uses as the scope — it pins at `top: 88px` while `.menu-content` still has room below the viewport's top edge, then unsticks the moment `.menu-content`'s own bottom edge scrolls past that point, which in practice lines up with the end of the section. `.menu-photo`'s own `position: sticky` a few rules away is a separate, independently-scoped thing (scoped to the photo column, not the tab row).

**No group panel behind the pills — three attempts to get there.** First version gave `.tabs` its own `var(--glass)` + `backdrop-filter: blur` background, which — even after trying to shrink it to `width: fit-content` — still read as a big solid rectangle once the 6 tabs wrapped to two rows, since the wrapped row's own width is nearly as wide as the column anyway. Dropping that background entirely exposed a real bug: once nothing painted over the gaps around/between the pills, a menu item that had scrolled up level with (or past) the tab row showed through those gaps — a heading like "Beef Taquitos" squeezed in behind/above the pills. Second attempt covered that gap with an opaque `background: var(--bg)` on `.tabs-sticky` itself (plus pseudo-elements extending the same flat color both above and below it) — technically not a *translucent* panel anymore, but a flat rectangle sitting on top of the page's ambient-glow background still read as a visible panel by eye, just a differently-colored one, not "no panel."

Current version drops the covering rectangle entirely — `.tabs-sticky` is pure positioning (`position: sticky; top: 88px; z-index: 40;` and nothing else), `.tabs` has no background of its own either, and each `.tab` pill floats on just its own solid `var(--surface)` fill, the same way `.shortcut-nav`'s own pills do. What actually closes the gap this time is real: `.menu-item` itself fades its own **opacity** out via a scroll-driven CSS animation as it nears the top of the viewport (see "Menu row layout" below) — the row becomes genuinely transparent before it would reach the pills, rather than being hidden behind something opaque painted on top of it. Once the content itself is gone, there's nothing left needing a backdrop to hide.

## File structure

- `index.html` — page skeleton and section order
- `fi/index.html` — generated from `index.html` by `scripts/prerender.mjs`, never hand-edited; see "Finnish URL"
- `style.css` — all visual styling
- `script.js` — loads data, calls each component, wires up interactions
- `components/` — one reusable "template" per repeating piece (dish card, the dish carousel that stamps them out, menu row, event card, gallery mosaic tile, button) plus one-off pieces (nav, mobile nav overlay, footer, language switcher, the special-event modal, the item detail modal, the gallery overlay and its single-photo viewer, the FAB, the Visit-section map) plus small shared helpers with no template of their own (`dishImage.js`'s filename-slugify lookup, `priceDisplay.js`'s price/wine-grid markup, `eventsLogic.js`'s Europe/Helsinki next-occurrence math — see "Events")
- `data/menu.json` — dishes and full menu content
- `data/site.json` — address, hours, reservation link, socials
- `data/events.json` — upcoming/recurring events; see "Events"
- `data/i18n/` — `en.json` / `fi.json`, one matching set of UI-chrome translation keys each
- `data/gallery.json` — generated by `scripts/build-gallery.mjs`, never hand-edited; see "Gallery"
- `images/` — photos, organized by section (`hero/`, `dishes/`, `logo/`, `og/` — the Open Graph share image, see "SEO", `gallery/<album>/`, `gallery-thumbs/<album>/` — the last two also generated/maintained by the build script, see "Gallery"). Every file in `dishes/` is also load-bearing for the dish-name filename convention (see "Dish photos: filename convention") — a file gets picked up automatically by any dish/menu item whose name slugifies to match it.
- `scripts/build-gallery.mjs` — optimizes `images/gallery/` photos and writes `data/gallery.json`; see "Gallery"
- `scripts/build-hero.mjs` — generates the hero's responsive AVIF/WebP/JPG variants from the untouched sources in `images/hero/`; see "Hero photo"
- `scripts/prerender.mjs` — writes the static menu/contact/events HTML inside `index.html` and generates `fi/index.html` from it; see "SEO", "Events", and "Finnish URL"
- `components/dishImageDims.js` — small shared lookup of `images/dishes/`'s real pixel sizes, used wherever one of those files gets an `<img width height>`; see "SEO"
- `robots.txt` / `sitemap.xml` — crawler access and the sitemap; see "SEO"
- `404.html` — on-brand 404 page served by GitHub Pages; see "SEO"
- `docs/HOW-TO-ADD-AN-EVENT.md` — plain-language, non-coder steps for editing `data/events.json` on github.com; see "Events"

## Special events or inquiry

The "Special Events or Inquiry" action opens a modal (`components/eventModal.js`) with a plain form — event type, preferred date, guest count, details. It's reachable two ways: the primary (filled) button in the Visit section, listed ahead of the now-secondary (ghost) "Reserve a Table" button, and a persistent floating action button (`components/fab.js`) fixed to the bottom-right corner of every section. Both triggers call the same exported `openEventModal()` — there's only ever one modal instance in the DOM, not two.

Event type is a `<select>` (Birthday / Private Party / Corporate Event / Anniversary / Other) rather than free text, since a dropdown covers the realistic cases with less typing; selecting "Other" reveals a small text input for the visitor to specify, which is only included in the mailto body when Other is actually chosen (`Event type: Other — [their text]`; otherwise just `Event type: <selected>`). On submit the form builds a `mailto:` link from the field values (no backend, no network call) and hands off to the visitor's own email client via `window.location.href`, then closes. A plain-text fallback line under the Visit-section buttons spells out the email address directly, in case the visitor's device has no mail client configured and the mailto link does nothing visible.

The FAB sits at `bottom: 24px; right: 24px` (`z-index: 90`, below the modal's 100 but above ordinary content) — independent of the top-anchored `.shortcut-nav`/`.utility-bar`/`.mobile-topbar`, so the two never compete for space. Below 720px it drops its text label and becomes a plain 52px circular icon button, matching the site's tactile "3D" button shadow language at any size.

The gap between the Visit section's heading and these buttons is tighter than every other section's heading-to-content gap (`#visit .section-head { margin-bottom: 28px; }`, vs. `.section-head`'s shared 60px default) — scoped to just this section rather than changing the shared rule, since heading-then-buttons reads better as one close-knit cluster here than the other sections' heading-then-a-full-content-row spacing does.

## Map

The Visit section's map (`components/map.js`) is [Leaflet](https://leafletjs.com/) loaded from a CDN, with plain OpenStreetMap tiles. It's centered on `data/site.json`'s `coordinates` field ({ lat: 60.1903, lng: 24.9535 }, geocoded for Aleksis Kiven katu 17), at zoom 16 — close enough to read the street. Scroll-wheel zoom is off by default so the map doesn't hijack an ordinary page scroll when the visitor's cursor happens to pass over it; drag-pan, the +/- controls, and pinch/double-click zoom all still work.

OSM only ships one (light) tile style — CartoDB's free Dark Matter/Positron tiles (used originally) now require a registered API key on a live domain, which showed up as a watermarked "API key required" tile instead of a map. A dark tint is simulated instead with an unconditional CSS filter applied to `.leaflet-tile-pane` specifically, not `.map-card` as a whole. Since Leaflet keeps tiles, markers, and popups in separate panes, scoping the filter to the tile pane means it never touches the marker or popup: the pin keeps matching `var(--accent)` exactly instead of also getting inverted.

The filter is `invert(100%) hue-rotate(180deg) brightness(1.2) contrast(0.82) saturate(0.6)`. An earlier version used `invert(90%) hue-rotate(180deg))` — a partial invert, which doesn't cleanly land the hue-preserving math the classic "dark-mode-via-invert" trick relies on (that trick assumes a full invert). Worked out against Standard OSM's actual palette (water `#aad3df`, park green `#cdebb0`, the road casing stroke `#a9a9a9`, the cream land fill `#f2efe9`), `invert(90%)` alone also crowded roads, buildings, and the land fill into a narrow, very dark 25–70 (out of 255) range where they're hard to tell apart — the road casing stroke in particular, the actual line that reads as "a road" in OSM's default style, ended up barely lighter than the land fill behind it. `invert(100%)` is the full version of the trick (white ↔ black, hue roughly preserved for saturated colors); `brightness(1.2) contrast(0.82)` lifts and compresses that same dark cluster so the road casing reads as a clearly lighter gray against the land fill instead of nearly merging into it, and `saturate(0.6)` pulls hue-rotate's output back further than the original `saturate(0.85)` did. Re-checked (same filter-math approach, not a tile screenshot — this sandbox can't reach tile servers) against the muted-palette repaint: at `saturate(0.85)`, water landed a distinctly saturated teal-blue that read too vivid next to the calmer new palette; `saturate(0.6)` pulls it to a near-neutral slate-grey much closer to `--bg-alt`, and OSM's major-road fill (a warm orange-yellow) lands in the same brass-grey family as the new `--accent` rather than reading as its own, unrelated orange. Worth a visual spot-check on the live site regardless, since none of this was eyeballed against real rendered tiles.

The pin is a plain `L.divIcon` (a styled `<div>`, not a raster pin image) — `.map-marker` in `style.css` builds a classic pin silhouette (circle + triangular tip) purely from `var(--accent)`, so it follows the palette exactly like every button/price/heading elsewhere. Leaflet's own chrome (the popup, the attribution line — kept visible, small, in the map's corner, since OSM's usage terms require it) is re-themed the same way, off `var(--surface)`/`var(--ink)`. The map card itself reuses `.visual`'s exact treatment (`border-radius: 22px`, `overflow: hidden`, `box-shadow: var(--card-shadow)`) — the same look as the dish/gallery tiles.

"Get Directions" (`#visit-directions`, styled `.btn-ghost`) sits directly under the map card and opens `https://www.google.com/maps/dir/?api=1&destination=<site.address>` in a new tab — the universal Google Maps link format, which works cross-platform (including handing off to Apple Maps on iOS via Google's own redirect) without any separate device-detection logic.

Section order is heading → the two CTA buttons → the "Or email us directly at…" fallback line (small gap, reads as one cluster with the buttons) → a larger gap → the map card → Get Directions (small gap, reads as the map's own action).

Leaflet loads from a CDN classic `<script>` ahead of the deferred module `script.js`, so its `renderMap()` call sees a ready global `L`. That call is wrapped in a `try`/`catch` in `script.js`: an ad blocker, privacy extension, or a transient CDN hiccup leaving `L` undefined costs the page a map, not the rest of `init()` (footer, menu tabs, gallery, translations all still run regardless).

## Menu row layout

`components/menuItem.js` stacks every row the same way regardless of category: name (free to wrap to multiple lines), then description, then price, one under the other — never sharing a line with the name. That's what makes wine's four-column price grid (and any other long name) line up cleanly instead of fighting for horizontal space or ending up vertically off-center against wrapped text. Only items with a real `image` in `data/menu.json` get a thumbnail; everything else renders text-only, full-width, with no placeholder box.

On desktop (`min-width: 901px`), a wine row switches from that stacked layout to name and its 12cl/16cl/24cl/Bottle price grid sharing one line (`.menu-item--wine .menu-item-body { flex-direction: row; justify-content: space-between; }`) — there's enough horizontal room there that stacking just wastes vertical space, and the name/labels are sized up slightly (28px name, 19px price value) since they're no longer competing for width. `menuItem.js` computes the `menu-item--wine` class straight from the price shape (`typeof item.price === "object"`) rather than a category name, so it's automatically only wine rows, and only wine rows have that 4-column price object in the first place. Below 901px this is untouched — same stacked layout and sizing as every other item.

Rows are clickable now (see "Item detail modal"), so hovering one gives a clear "this is interactive" cue rather than looking like a hover accident: a thin `var(--accent)` bar fades in at the left edge (`.menu-item::before`, inset top/bottom so it doesn't clip through the row's own `border-radius` at the corners), the whole row nudges 6px right (`transform: translateX(6px)`), and the existing subtle background tint still applies — all on one `0.2s` transition so it reads as one smooth "row lifting toward you" motion rather than several separate effects firing independently.

Each row also fades its own opacity out as it scrolls up near the pinned category tabs (`#menu .menu-item, #menu .menu-note, #menu .menu-group-heading`, inside `@supports (animation-timeline: view())`) — the same view-timeline technique "Scroll reveal" above uses to fade rows *in* on the way down, running in reverse, driven by the row's own exit from the viewport rather than its entry: `animation: menuItemFadeOut linear both; animation-timeline: view(); animation-range: exit -220px exit -90px;`. Negative offsets on an `exit` range move the trigger point *earlier* than the named phase's own `0%` — `exit -220px` starts the fade while the row's top edge is still ~220px down the viewport (comfortably below the tabs), and `exit -90px` finishes it while the top edge is still ~90px down, i.e. essentially fully transparent by the time the row would reach the tabs' own `top: 88px`, not still fading (or popping back) once it's behind them. This exists specifically so `.tabs-sticky` doesn't need a covering background at all (see "Shortcut nav" above) — the row itself is what disappears, not something painted over it.

`.menu-note` (the Lunch tab's price/schedule line, Cocktails' tequila note — `appendGroupNote()` in `script.js`) and `.menu-group-heading` (the Drinks tab's Soft Drinks/Beer/Cocktails/Wine sub-headings) needed the exact same selector added explicitly — they're direct children of `#menu-list` sitting right alongside `.menu-item` rows, in the identical "scrolls up toward the tabs" situation, but the first version of this only covered `.menu-item` and missed them, so the Lunch note in particular was left showing through above the tabs exactly like an unfaded `.menu-item` would.

## Item detail modal

Clicking (or focusing + Enter/Space on) any menu row or signature dish card opens a shared detail modal (`components/itemModal.js`) — a large photo (or a small photo strip, see below), the full name, description, allergen tags, and price (reusing `priceDisplay.js`'s exact price/wine-grid markup, so the modal's price section looks identical to the row it was opened from). `itemModal.js` doesn't know or care which of the two list styles opened it; both just call `openItemModal(item)` with the plain object they already had on hand (`{ name, price, allergens, description, image, images? }`).

It reuses `.modal-overlay`/`.modal-card`/`.modal-close` — the exact same system the Special-Event-Inquiry modal uses — so the two read as one modal system rather than two different ones; only what's actually different gets its own rules (`.item-modal-*` in `style.css`): a much larger card (640px vs. the event modal's 460px — this is meant to be a proper "look at this dish" moment, not a compact popup; full-screen below 720px), a photo bleeding to the card's own top edge, a fade/scale-in entrance animation, and a contrast-safe close button treatment for sitting on top of a photo. When there's no matching photo, the image area collapses to a small stylized accent-glow strip (`.item-modal-photo--empty`, the same radial-gradient-pair technique `.menu-photo-ambient`/`.section-ambient` already use elsewhere) instead of either a broken-image icon or a large empty photo-shaped hole.

**The close button didn't actually close the modal — only clicking the backdrop did.** Root cause: `.item-modal-photo` (the photo area) is `position: relative`, sits AFTER the close button in the DOM, and neither element had an explicit `z-index`. Among sibling elements that are all "positioned" (any position other than `static`) with `z-index: auto`, later DOM order wins the paint order regardless of visual intent — so the photo (and its `<img>`) was silently painting on top of the button and swallowing every click aimed at it; the click landed on the photo, bubbled up, and didn't match either of the overlay's own close conditions (`event.target === modal` or `.closest("[data-close-modal]")`). Fixed with an explicit `z-index: 5` on `.item-modal-close` — the kind of bug that's invisible reading the HTML/JS in isolation and only shows up once you check what's actually painting on top of what.

A dish with more than one photo (`images` in `data/menu.json` — Quesabirria is the only one right now) gets a small tappable thumbnail strip under the primary photo; clicking a thumbnail swaps the primary image and highlights that thumbnail. Deliberately simple (swap `<img src>`, no carousel/swipe machinery) since it's a rare case — most items have at most one photo and never render a strip at all.

Every row/card is now genuinely interactive where it wasn't before, so this also added `role="button"`, `tabindex="0"`, and an `aria-label` (the item's name) to each — plus a keydown handler treating Enter/Space the same as a click. One knock-on fix this required: the signature dish carousel renders its card list twice back-to-back for its seamless-loop trick (`dishCarousel.js`), with the second copy marked `aria-hidden="true"` for screen readers — but `aria-hidden` alone doesn't remove an element from the keyboard Tab order, so without an explicit `tabindex="-1"` on that duplicate set's cards, Tab would visit every dish's clickable card twice in a row. `dishCarousel.js` now sets that explicitly on the hidden copy's cards.

## Full Menu image column

The Full Menu section was a single narrow list column with large empty margins on desktop. It's now a two-column layout mirrored from the Story section (`.menu-layout`, image + content), but flipped: Story is text-left/photo-right, so Menu is photo-left/content-right, giving the page an alternating rhythm instead of two identical-looking split sections. Same DOM-order technique as Story — the photo column is first in the markup, content second, so a plain `flex-direction: row` on desktop already puts photo-left with no reversal trick; mobile uses `column-reverse` (not `column`) so the list — what a visitor actually came for — shows first and the photo stacks below it, consistent with "reverse the same DOM order" rather than a separate mobile-only arrangement. The split favors the list over an even 50/50 (`flex: 0 1 42%` photo / `flex: 1 1 60%` content) so item descriptions and the wine price grid keep their room. The photo column is `position: sticky` on desktop so it stays in view while a long category (e.g. tacos, 9 items) scrolls past it.

`components/menuPhoto.js` drives the column's contents: a small (2-3 image) rotating, crossfading set per active category tab, swapped by `renderMenuCategory()` in `script.js` on every tab click. There's no dedicated photography per category yet, so `CATEGORY_IMAGES` reuses existing `images/dishes/` photos as filler, loosely on-theme rather than claiming to depict a specific dish (same "known gap, swap later" approach as the gallery). Desserts has no photo at all in the map — none of the existing shots are dessert-appropriate, and showing a savory dish under that tab would actively mislead rather than just look generic — so it falls back to the same radial-glow ambient treatment `.section-ambient` uses elsewhere (`.menu-photo-ambient`, shown only when the active category's image list is empty). A leaked `setInterval` was a real risk here since the rotator restarts on every tab click and every language switch (which also re-renders the active category) — `showCategory()` always `clearInterval`s the previous timer before starting a new one; verified stable under repeated switching.

**Tonal wash + larger column — started as a Menu-only test, since brought to Story too.** Even with the soft-fade edges, the photo still read as a small floating box against a lot of empty section background rather than something that blends in. `.menu-photo`'s max-width went from 420px/440px (mobile/desktop) originally to 480px/520px in that pass, and the gap between the photo and content columns from 48px/56px to 32px/40px.

**Follow-up: a wider fade band.** Compared directly against a reference site's menu photo treatment, the first pass above still read as a rectangle with softened corners rather than something genuinely dissolving into the background — `.soft-fade-img`'s default `--fade-edge: 20%` only lets the outer fifth of the image fade, leaving most of it looking like an ordinary photo with a vignette. `.menu-photo-img, .menu-photo-wash { --fade-edge: 42%; }` overrides just that custom property (not `.soft-fade-img`'s own gradient/mask rules, so nothing else sharing the class was affected yet) — at 42%, only the innermost 16% of the photo stays fully opaque and nearly the whole image participates in the fade, which is what actually reads as "naturally disappearing" rather than a wider soft border.

**Brought to Story too, once it read right on Menu.** Same `--fade-edge: 42%` override, plus a `.story-photo-wash` element mirroring Menu's, added right next to the existing `.story-photo`/`.story-photo-img` rules. The concern going in was whether 42% would eat into the photo's actual subject (the glass and hand), not just its blurred background — checked directly first (Menu's own Drinks tab reuses this exact `tommys-margarita.jpg` file), confirmed the glass and hand stayed sharp inside the fully-opaque core with only the bokeh background and outer edges fading.

**The wash went flat → radial → flat again, settling on a much lighter flat tint.** `.menu-photo-wash`/`.story-photo-wash` started as a single flat `color-mix(in srgb, var(--bg) 45%, transparent)` layer — simple, but 45% darkened the *center* of the photo (where the dish/subject sits) by exactly as much as the edges, dulling the subject along with them. That was replaced with a radial gradient (barely touching the center, ramping up to a full `var(--bg)` blend at the edge, reinforcing the `--fade-edge` mask), which fixed the center but over-corrected at the edges — the ramp-to-full-`var(--bg)` stacked on top of the mask's own edge falloff read as *too* dark right where the mask was already dissolving the photo. Current version: back to flat, but at 12% instead of the original 45% (`color-mix(in srgb, var(--bg) 12%, transparent)`, uniform across the whole photo) — light enough that the subject stays close to its natural brightness everywhere, leaving the 4-side `--fade-edge` mask as the only thing doing edge falloff rather than the wash doing its own competing version of the same job. Columns were also sized up a further notch in an earlier pass: Menu's `.menu-photo` to 510px/560px (mobile/desktop, flex-basis 44%), Story's to 460px/520px.

**`--fade-edge` settled at 18%, after overshooting in both directions.** The mask went through the same back-and-forth as the wash: 20% (`.soft-fade-img`'s shared default) read as barely-there, so Menu/Story overrode it to 42% — which then over-corrected, leaving only the innermost 16% of the photo (42–58%) fully opaque and fading well over a third of the image in from each edge. Dropping it to 4% over-corrected the *other* way: with such a narrow band, the fade stopped reading as a soft blend at all and looked more like a sharp, almost hard edge. `--fade-edge` is both "how far the fade reaches inward" *and* "how wide the fade band is" in `.soft-fade-img`'s gradient (`transparent 0%, black var(--fade-edge), …` — the fade starts at the image's own edge and finishes at that percentage, so there's no separate "start position" to move independently of "width"), and it turns out that width has a real lower bound for reading as "soft" rather than "clipped," independent of how smooth the underlying gradient math is. 18% is the number that landed between "over-corrected wide" (42%) and "over-corrected narrow" (4%): a fully-clear center covering 64% of the photo (18–82%), with a wide enough band at the edges to actually look like a gradient. Applied identically to both `.story-photo-img`/`.story-photo-wash` and `.menu-photo-img`/`.menu-photo-wash`.

## Gallery

Rebuilt from the ground up around a simple goal: the owner keeps adding photos by dragging files into folders on github.com, with no code or JSON edits ever needed. See "Adding gallery photos" below for that workflow; this section covers how it's built.

**Data source.** `data/gallery.json` is generated — never hand-edited — by `scripts/build-gallery.mjs` from whatever's actually sitting in `images/gallery/<NN-album-name>/`. It's `{ albums: [{ slug, title: {en, fi}, count, photos: [{src, thumb, w, h}] }], total }`. `w`/`h` are the *optimized* (post-resize) dimensions, used everywhere a tile needs to reserve its own aspect-ratio before the image loads, so nothing reflows. Albums with zero photos are left out of the file entirely — the simplest way to guarantee they're "hidden from the album pills" is to just not ship them to the UI at all, rather than trusting every surface that reads the file to remember to filter empty ones. If `data/gallery.json` is missing outright (a fresh checkout before the script has ever run) or every album is empty, `script.js` hides the whole Gallery section and both its nav links (`document.querySelectorAll('[data-section="gallery"]')`) instead of showing an empty teaser.

**Folders and album metadata.** Each `images/gallery/` subfolder is one album; the leading number sets display order and is stripped from the title (`01-summer` → "Summer"), hyphens become spaces, and the whole-word "and" becomes "&" (`04-food-and-drinks` → "Food & Drinks") — see `titleFromFolderName()` in the build script. An optional `album.json` inside a folder (`{"title": {"en": "...", "fi": "..."}}`) overrides that derived title; all four current albums have one, with Finnish titles written by Claude and **flagged here for native review**: Summer → Kesä, Special Events → Tapahtumat, The Room → Tila, Food & Drinks → Ruoka & juomat. Without an `album.json`, the Finnish title just reuses the English one verbatim (a real gap, not a translation) rather than guessing. `04-food-and-drinks/` is currently seeded with copies of the same 7 dish photos from `images/dishes/` used elsewhere as filler — real event/room/food photography can replace them whenever it exists; `03-the-room/` and the rest are empty folders (just a `.gitkeep`) ready for real photos, since no interior photo was available to seed this pass.

**Optimization pipeline (`scripts/build-gallery.mjs`, via `sharp`).** For every accepted file (`.jpg`/`.jpeg`/`.png`/`.webp`, case-insensitive — anything else, HEIC included, is skipped with a console warning rather than silently ignored or crashing the run): auto-orient from EXIF (`sharp(...).rotate()` with no arguments reads the EXIF orientation tag and bakes the rotation in), then re-encode *without* `.withMetadata()` — sharp strips all input metadata by default unless you explicitly ask it to keep it, which is what removes EXIF (GPS included) from the output. Originals are resized to fit within 2000px on the long edge (`fit: "inside", withoutEnlargement: true` — never upscales a smaller photo) at quality ~82 (`mozjpeg` for JPEG, native quality for WebP, max `compressionLevel` for PNG), overwriting the same filename/extension in place. **Idempotent by construction**: a file is only reprocessed if its long edge exceeds 2000px *or* it still carries an EXIF buffer — checked via a `sharp(...).metadata()` read before touching anything — so a second run against already-optimized photos changes zero bytes (verified directly: `md5sum` before/after a repeat run matches exactly). Thumbnails (long edge 900px, quality ~75, same filename, same format) land at `images/gallery-thumbs/<album>/<file>`, outside the path the Action watches, regenerated only when the original changes or the thumbnail doesn't exist yet; a thumbnail whose original has been deleted is removed on the next run, and an entire `gallery-thumbs/<album>/` folder is removed if its album folder is now empty or gone.

**The Action (`.github/workflows/gallery.yml`).** Runs on every push to `main` touching `images/gallery/**`, plus manual dispatch. No `package.json`/`package-lock.json`/`node_modules` is committed — `npm i --no-save sharp` installs it fresh in the job (and the same way for a local run), matching how `node scripts/build-gallery.mjs` is meant to be run by hand too. Commits only if `git diff --cached` actually finds a change (so an already-optimized push through — someone editing an unrelated file inside `images/gallery/` — doesn't produce a no-op commit), as `github-actions[bot]`, with `git pull --rebase` immediately before the push in case `main` moved while the job was running, inside a `concurrency` group keyed to the branch so two pushes in quick succession queue instead of racing each other's commit. A final step `POST`s to `/repos/{owner}/{repo}/pages/builds` after a successful commit — pushes made with the default `GITHUB_TOKEN` don't reliably trigger GitHub Pages' own build-on-push depending on how Pages is configured for this repo, so this asks for a rebuild explicitly rather than assuming the commit alone was enough; harmless if Pages was already going to rebuild on its own. `permissions: contents: write, pages: write` — nothing broader.

**Main-page teaser (`components/galleryMosaic.js`).** One big tile (spanning both rows) plus two smaller tiles, a 1.4fr/1fr column split so the big tile reads as the hero of the three; `aspect-ratio` (not a fixed pixel height) lets the same grid structure scale between mobile and desktop with only `gap`/`border-radius` adjusting at the breakpoint. Each page load, 6 photos are picked at random across *all* albums (Fisher-Yates shuffle, not just slicing a sorted list — avoids both a sampling bias toward whatever sorts first and any chance of the same photo in two tiles), using thumbnails. Each tile independently crossfades between its 2 photos on a 12-second loop, staggered 4 seconds apart so the three don't flip in unison — same stacked-`<img>`/`--active`-class opacity-toggle mechanic the Menu section's rotating photo column uses. `prefers-reduced-motion: reduce` skips starting the loops entirely (static photos, not a faster version of the same animation). Tiles are `<button>`s now, not `<div>`s — clicking any one of them opens the full gallery, same as the "See all N photos" button under them (`gallery.seeAllPhotos`, a `{count}`-templated i18n string, not a fixed "See All Photos" label).

**Full gallery overlay (`components/galleryOverlay.js`).** A dedicated full-screen layer (`z-index: 150`, not the `.modal-overlay`/`.modal-card` system the event/item modals use — this needs to *be* the page while open, with its own internal scroll region, not a centered card over one). Header + close button and the album pill row (`.tab`'s own styling, reused — "All" first, then one pill per non-empty album with its photo count) travel together as one `position: sticky` unit at the top of `.gallery-overlay-scroll`, the element that actually scrolls. Every photo across every album renders as one `<button class="gallery-tile">` up front, in a CSS-columns masonry (`column-count`: 2 mobile / 3 tablet / 4 desktop, `break-inside: avoid`, ~12px gaps) — each tile's own `w`/`h` from `gallery.json` set its `aspect-ratio` inline, so switching albums or scrolling never causes a reflow. Choosing a pill doesn't re-render anything; it toggles a `--filtered-out` class (opacity 0 + `pointer-events: none`, not `display: none`, so there's something to actually fade — the tradeoff is a filtered-out tile still briefly occupies its column space during that ~200ms transition) on every tile that doesn't match, which is also simpler than tracking per-album DOM subtrees.

**The "developing" reveal.** Each tile's photo starts `grayscale(1) blur(10px) brightness(0.5) scale(1.04)` and animates to normal over 900ms the first time it scrolls into view (`IntersectionObserver`, `threshold: 0.1`, un-observed immediately after triggering — it only ever plays once per tile, never again on re-entry). A nod to "Klandestina" meaning clandestine: a print developing in a darkroom. Entirely inside `@media (prefers-reduced-motion: no-preference)` — a visitor with reduced motion gets every tile already in its finished state, with no filter/transform to transition away from at all, rather than a fast version of the same animation.

**Single-photo viewer (`components/galleryPhotoViewer.js`).** Opened from a tile at that photo's position within whatever's *currently filtered* in (not always the full album set) — `object-fit: contain` at full optimized-original size (not the thumbnail), with the next and previous photos preloaded (`new Image().src = ...`) as soon as the current one renders. The backdrop is an ambient glow built from the photo itself: two stacked, absolutely-positioned, oversized `background-image` layers (`blur(60px) saturate(1.4) brightness(0.45)`) crossfading into each other on every photo change — same two-element opacity-toggle trick as the mosaic tiles, just driving a CSS filter stack instead of per-`<img>` loading state. The same "developing" reveal plays on open and on every photo change, shorter (500ms) and a little lighter than the masonry grid's version, replayed by removing and re-adding its animation class with a forced reflow in between (`void img.offsetWidth`) — re-adding an already-present class doesn't restart a CSS animation on its own. Desktop gets prev/next arrows and an auto-scrolled thumbnail filmstrip (`scrollIntoView({inline: "center"})` on the active thumb); both are hidden on mobile, where swipe left/right navigates and swipe down closes (plain `touchstart`/`touchend` delta tracking, 50px threshold). Keyboard: ←/→ to navigate, Esc to close, Tab trapped inside the viewer while it's open.

**Browser-back handling.** Opening the overlay pushes one `history` entry; opening the viewer from inside it pushes a second — with no URL change (`history.pushState(state, "")`, omitting the url argument), since `#gallery` is already a real anchor the nav pills jump to and changing the hash here would fight that. A single `popstate` listener (in `galleryOverlay.js`) closes whichever layer is currently open, innermost first. Every in-app close action (the × buttons, Esc, swipe-down) calls `history.back()` rather than closing directly — so there's exactly one place that actually hides either layer (the `popstate` handler), and the browser's own Back button, Esc, and tapping × all produce the identical "close the lightbox, then the gallery, never both at once" behavior rather than three slightly different implementations of the same thing.

**i18n.** `gallery.seeAllPhotos`/`photoCounter`/`photoOfTotal`/`altPhoto` are `{placeholder}` templates, not fixed strings — `t(path, vars)` in `script.js` grew a small optional second argument (`{current}`/`{total}`/`{album}`/`{n}`/`{count}` substitution via `String.replaceAll`) to support them; every other call site just omits it and gets the plain string back, so this didn't touch any existing translation. `script.js` is still the only place that calls `t()` — the gallery components receive a `labels` object of plain strings plus a few small closures (`counterFn(current, total)`, etc., for the handful of strings that need fresh numbers substituted on every navigation rather than once at render time) built by `buildGalleryLabels()`, the same "components don't know about i18n" split `dishCarousel.js`'s `{prev, next}` labels already established. Album titles come pre-resolved to a plain string too (`resolveGallery()` picks `title[currentLanguage]` out of the raw `{en, fi}` data) rather than components ever seeing the raw bilingual object. Language switching re-renders just the chrome text (header, pills, CTA button) via `refreshGalleryOverlayLabels()`/`refreshGalleryMosaicLabels()`, not the whole masonry grid — rebuilding that would reset scroll position and silently re-trigger every tile's "developing" animation for no reason. One known gap: a `.gallery-tile`'s own `aria-label` is set once at render time and won't update if the language changes while the overlay happens to be open — an edge case judged not worth a full grid re-render to close.

### Adding gallery photos

No code or JSON editing — this works entirely through github.com:

- **Add photos to an existing album:** go to `images/gallery/<album>/` on github.com (e.g. `images/gallery/04-food-and-drinks/`), **Add file → Upload files**, drag in any number of `.jpg`/`.jpeg`/`.png`/`.webp` files of any size (the Action shrinks and optimizes them automatically — there's no need to resize or compress anything first), and commit. Allow roughly 2–3 minutes for the Action to run and for GitHub Pages to republish.
- **Start a new album:** open `https://github.com/sarojaryal071-sudo/klandestina/upload/main/images/gallery/05-your-album-name` directly (bump the leading number past whatever's already there), drop at least one photo in, and commit — the folder itself becomes the new album with no further setup. Add an `album.json` next to the photos (`{"title": {"en": "...", "fi": "..."}}`) if the title the folder name would derive on its own isn't right.
- **Remove a photo:** delete the file from its album folder on github.com; the next Action run removes its now-orphaned thumbnail automatically.
- **Ordering:** the album folder's leading number controls album order; photo filenames (sorted naturally — `IMG_2` before `IMG_10`) control photo order within an album.

## Events

`data/events.json` is a flat array of events — `{ id, type, weekday (recurring) or date (oneoff), startTime, endTime, title, description, tag, price, image }`. `type` is `"recurring"` or `"oneoff"`; `weekday` is 1–7 (Monday=1, so "Friday=5"), only used when `type` is `"recurring"`; `date` is a plain `"YYYY-MM-DD"` string, only used when `type` is `"oneoff"`. `startTime`/`endTime` are `"HH:MM"` 24-hour strings, both optional, and `endTime` reading numerically "earlier" than `startTime` means the event runs past midnight. `title`/`description`/`tag`/`price` are `{en, fi}` objects — `price` is optional and genuinely left unset when the event doesn't have one (the seeded Halloween entry), never invented. `image` is optional, a filename inside `images/events/`. See `docs/HOW-TO-ADD-AN-EVENT.md` for the plain-language, non-coder editing workflow on github.com; this section covers how it's built.

**Next-occurrence math (`components/eventsLogic.js`).** No date library — Europe/Helsinki local time is computed purely from the `Intl` API already built into both the browser and Node (the same runtime `scripts/prerender.mjs` already relies on), via the standard "format an instant into a timezone, re-read those numbers as if they were UTC, subtract" offset trick, refined once against its own first guess. A recurring event's `nextOccurrence()` checks yesterday, today, and the next 7 days for a matching weekday and returns the earliest candidate whose window (`start`, and `end` if given) hasn't fully elapsed — checking **yesterday first** is what makes a Friday-night event that runs past midnight keep reporting Friday's own start time, rather than jumping ahead to the following Friday, for as long as it's still actually going (the task's "a night running past midnight counts as tonight until its end time" rule). A one-off's occurrence is just its `date` at `startTime`; once its effective end passes — or, for an event with no time at all, once its calendar date itself has passed — `nextOccurrence()` returns `null` and `resolveUpcomingEvents()` drops it from the result entirely, no archiving flag needed. `script.js` and `scripts/prerender.mjs` both call the exact same functions for this (see "Prerendering" below) rather than keeping two timezone implementations in sync by hand.

**UI (`components/eventsSection.js`).** Renders the sorted, resolved list as a column of cards between Menu and Gallery (`#events` — the plain dark `:root` surface, no `.surface-light`/`.surface-white`, so the white→dark→light rhythm across Menu/Events/Gallery doesn't repeat the same surface back to back). The soonest occurrence — always index 0, since `resolveUpcomingEvents()` already sorts by it — renders larger, as `.event-card--hero`, with a brass accent wash and a filled date block (the same `--accent-fill`/`--on-accent` pairing `.btn-primary` already uses, already verified ≥4.5:1 — see "Palette"); any card whose resolved `isTonight` flag is true also gets an outlined "Tonight"/"Tänään illalla" badge. Hidden entirely — the `<section>` and its `[data-section="events"]` nav links (`components/nav.js` and `components/mobileNav.js` both hardcode `events` into their own `SECTIONS` list, same as `gallery`) — the moment `resolveUpcomingEvents()` returns an empty array, the same "hide rather than show empty" rule Gallery already follows when it has no photos.

**Prerendering + JSON-LD (`scripts/prerender.mjs`).** Same shape as the menu/contact blocks (see "SEO" below): `data/events.json` is resolved once per run, not once per language, so `index.html` and `fi/index.html` always agree on exactly which events are upcoming — only their text differs. The script writes the identical card markup `eventsSection.js` renders client-side between `<!-- PRERENDER:EVENTS:START/END -->` inside `#events-grid`, plus one schema.org `Event` per upcoming occurrence between `<!-- PRERENDER:EVENTS_JSONLD:START/END -->` — `eventAttendanceMode: OfflineEventAttendanceMode`, `location` built from the restaurant's own address/geo in `data/site.json`, and an `offers` block of `{price: "0", priceCurrency: "EUR"}` added only when the event's English price text contains the word "free" (exactly what the karaoke seed's "Free entry" is). A genuinely-priced event gets no `offers` block at all rather than a guessed number — `data/events.json`'s `price` is display text, not a structured amount, and inventing one would be worse than omitting it. When there are zero upcoming events, the `<section id="events">` tag itself gets a literal `hidden` attribute spliced in and the JSON-LD marker pair is left empty, so a crawler or no-JS visitor sees exactly what a JS-enabled one eventually settles on — same guarantee the menu/contact blocks already make.

**Why the workflow also runs on a schedule.** Unlike the menu or the gallery, what counts as "upcoming" in `data/events.json` changes on its own, with no commit involved: a one-off's date passes, or a recurring event's occurrence rolls over to next week. `.github/workflows/prerender.yml` now runs on a daily `schedule: cron` trigger (`15 1 * * *`, just after Helsinki midnight) in addition to its existing push triggers, so an expired one-off (Halloween, the day after) drops out of the published `index.html`/`fi/index.html`/JSON-LD within about a day of actually expiring, instead of sitting there until some unrelated push happens to touch a watched file.

## Story and Menu photo edges: the soft-fade mask

The Story photo (and now the Menu image column) has soft, feathered edges rather than a hard rectangular crop — `.soft-fade-img` in `style.css`, shared by `.story-photo-img` and `.menu-photo-img`. It went through two wrong versions before landing on the current one:

- **First version rendered as a plain hard-edged rectangle with zero fade at all.** Every individual mask property looked correct (`mask-image`/`-webkit-mask-image` both set, the gradient's outer stop fully transparent, no leftover `border-radius`/`overflow:hidden` clipping, `mask-repeat`/`mask-size`/`mask-mode` all explicit), which pointed at something less obvious. Isolating the mask in a standalone test page found it: `radial-gradient(ellipse 70% 70% at 50% 50%, ...)` — an explicit percentage-pair ellipse size — silently produces no fade at all as a mask in this rendering engine. Swapping to `ellipse closest-side` (keyword-based sizing) fixed the fade itself, confirmed via pixel sampling across the edge.
- **That fix produced a fade, but the wrong shape**: a radial mask fades outward from the center in an oval, which shrinks the visible photo into a soft blob rather than keeping it a photo with feathered borders — the wrong effect, not a bug in that gradient's syntax.

The current version drops radial-gradient entirely. It's built from two `linear-gradient` mask layers — one fading the left/right edges (`to right`), one fading the top/bottom edges (`to bottom`) — each opaque through the middle ~60% and transparent in the outer `--fade-edge` (20%) band per side. The two layers have to **intersect** (multiply) rather than the default per-layer "add" compositing: under "add", a pixel near the left edge but vertically in the untouched middle band would sum to (low horizontal alpha) + (alpha 1 from the vertical layer) ≈ still opaque, so the left/right edges wouldn't actually fade except right at the corners. `mask-composite: intersect` (standard) plus `-webkit-mask-composite: source-in` (legacy WebKit/Safari syntax) make each layer cut into the one below it instead. Verified in a standalone test page (rectangular photo, sharp center, all 4 sides and corners feathered, no blob) and against the real Story/Menu photos with pixel sampling along the edge — a smooth ramp from background color at the very edge to fully photo-colored well inside it, not a falloff that reverses further into the photo the way a vignette's would.

Building the Menu photo column separately surfaced an unrelated layout bug: its image frame (`position: relative; width: 100%; height: 100%`, a normal-flow child) rendered at zero height, even though its parent (`.menu-photo`, sized via `aspect-ratio: 4/5`) measured correctly on its own. A percentage `height: 100%` doesn't reliably resolve against a flex item whose own height comes from `aspect-ratio` rather than an explicit value. Switching the frame to `position: absolute; inset: 0` (matching `.visual-img`'s existing pattern elsewhere in the codebase) sidesteps the percentage resolution entirely and fixed it.

## Image loading & size

Photos on a mobile connection were slow to appear, and several never showed up at all — visible as tiles stuck on `.visual`'s `background-color` fallback (`var(--surface-edge)` now; see "Palette"). Two compounding causes, both fixed:

- **Every dish photo was being downloaded twice.** The gallery had its own `images/gallery/` folder that was, at the time, a byte-identical copy of `images/dishes/`, used purely as filler — since browsers cache by URL, `images/dishes/tuna-poke.jpg` and `images/gallery/tuna-poke.jpg` were two separate downloads of the same bytes. `images/gallery/` was deleted at the time and the gallery pointed straight at `images/dishes/` instead. **This has since been reversed**: `images/gallery/` is back as a real, independent folder structure (see "Gallery") — the one duplicate-download tradeoff that reintroduces is `04-food-and-drinks/`'s seed copies of the same dish photos, accepted deliberately as filler content rather than an oversight, same as it was the first time.
- **The photos themselves were oversized originals** — one was 2576×1449 (757KB) for what only ever displays at a few hundred pixels wide at most. Resized every file in `images/dishes/` to a 1000px long edge and re-encoded at quality 78, which also strips the bulky EXIF data these happened to carry. Combined with removing the duplicate folder, total image weight for a full page visit dropped from roughly 3.3MB to under 500KB.
- **Dish cards and gallery tiles used a CSS `background-image`** instead of a real `<img>`. Background-images have no equivalent to `loading="lazy"`/`decoding="async"`, and browsers are inconsistent about deferring them for off-screen elements — on a page with a dozen-plus photo tiles, several were still sitting empty well after the ones above the fold had already loaded. Both components now render an actual `<img loading="lazy" decoding="async">` layered under the existing scrim/caption overlay (same visual result, `.visual-img { position: absolute; inset: 0; object-fit: cover; }` in `style.css`), matching what `menuItem.js`'s thumbnails already did correctly.

New dish photos should go in at a similar size (long edge around 1000–1200px is plenty for how large these ever render) rather than an unedited original straight off a phone.

## Mobile navigation

Below 900px, the desktop pill nav (`#shortcut-nav`) is hidden and has nothing standing in for it except the hamburger button in the mobile topbar (`components/mobileNav.js`). Tapping it opens a full-screen overlay — a "Klande·stina" wordmark (the same accent-dot treatment as the footer logo), then Home / Story / Menu / Gallery / Find Us with thin accent dividers between them.

Visually it's built entirely from the site's own tokens rather than a fixed color: the background is the same radial-accent-glow-over-`var(--bg)` treatment as `.hero`, and each link reuses `nav.js`'s pill-fill hover/tap pattern — a solid accent shape growing in behind the text (label and pill-fill are separate sibling spans, same split `nav.js` uses, so `applyTranslations()` re-setting the label's text never wipes the pill-fill out). The close button matches the site's raised-shadow/press-on-tap button language instead of a plain outlined circle.

The panel slides down from the top on open and back up on close (a container-level transform only — deliberately not an opacity fade, which briefly let the page behind it show through since the backdrop's own gradient would turn translucent too), while the wordmark and each link fade/rise in with a ~50ms stagger. Links call `preventDefault()` and drive the scroll themselves (`element.scrollIntoView()`) after the close animation actually finishes, rather than the previous approach of relying on the native anchor jump + site-wide `scroll-behavior: smooth` — needed so the overlay visibly closes before the page underneath jumps, instead of both happening at once. Scoped to `<=900px` only — both a `@media (min-width: 901px)` CSS guard and the fact that the toggle only exists inside the (itself hidden-above-900px) mobile topbar keep desktop nav behavior untouched.

Landing on a section used to leave a large, inconsistent gap under the fixed topbar (worst on Menu, since its tab row made the empty space obvious) — two compounding causes, both mobile-only fixes in the same `@media (max-width: 900px)` block in `style.css`: every `section` was still using desktop's 130px top padding, and none of the five nav targets (`#hero`/`#story`/`#menu`/`#gallery`/`#visit`) had a `scroll-margin-top` accounting for the topbar's height, so the browser scrolled each one flush to the very top of the viewport, right underneath (or behind) it. Mobile `section` padding is now `64px 24px`; the five targets get `scroll-margin-top: 85px` (the topbar's measured 69px height plus 16px of breathing room), landing each one with the same small, intentional gap instead.

That fix on its own wasn't enough, though: `initMobileTopbarAutoHide` (a plain scroll listener — hide on scroll down, show on scroll up) can't tell a nav-triggered jump apart from the visitor scrolling by hand, so it was hiding the topbar mid-jump — right as the visitor landed, with nothing left to justify the `scroll-margin-top` clearance reserved for it. A link click now sets `document.body.dataset.navJump = "true"` for the duration of its own `scrollIntoView()` call (cleared on the `scrollend` event, with a 1s timeout fallback for browsers without it) and force-shows the topbar first; the scroll handler skips its hide logic entirely while that flag is set. A second, unrelated bug reported alongside this: opening the site fresh sometimes landed mid-page instead of at the top — iOS Safari in particular can restore a tab's last scroll offset on a fresh visit to the same URL rather than starting at 0. `index.html`'s inline `<head>` script now sets `history.scrollRestoration = "manual"` to opt out of that; it has no effect on an intentional `#section` link, which is a separate browser mechanism.

## Brand mark / logo

Every place "Klandestina" renders purely as a wordmark/brand-mark — the desktop topbar (`#brand-mark`), the mobile fixed topbar, the mobile hamburger nav overlay, and the footer — goes through one shared function, `components/logo.js`'s `brandLogoHTML(site)`, rather than four separate hardcoded treatments. (Plain-prose mentions of "Klandestina" — Story body copy, the meta description, the footer's copyright line — are unrelated and untouched; this is only about the literal brand-mark treatment.)

`data/site.json`'s `logo` field points at the image file (`images/logo/klandestina-logo.png`). `brandLogoHTML()` renders an `<img alt="Klandestina">` at that path; if `logo` were ever unset, or the file went missing/failed to decode, it falls back to the exact same hand-typeset "Klande·stina" text mark the site always used (an `onerror` handler swaps the broken `<img>` for that text), so a missing or renamed logo file degrades gracefully instead of breaking the nav/footer layout. Sizing is CSS-only, one shared `.brand-logo-img` height per placement (`#brand-mark`, `.mobile-topbar-brand`, `.mobile-nav-brand`, `.footer-logo` in `style.css`) rather than separate image files per spot — sized up a second pass after the first felt too small next to the rest of the topbar chrome: desktop topbar 26px→38px, mobile topbar 24px→34px, mobile nav overlay 36px→46px, footer 42px→56px.

The provided file is white letter-fill with a black drop-shadow, drawn for a dark background. It was previously inverted under a light theme (`filter: invert(1)` on `.brand-logo-img`); that rule is gone along with the light theme itself (see "Palette" below) — the site is single-palette now, always dark, so the logo always renders as originally drawn with no conditional filter.

The favicon (`favicon.ico`) is generated from the same logo: since "KLANDESTINA" as a full wordmark would be illegible at 16–32px, it's cropped to just the "K" glyph, centered on a solid square canvas using the site's own background color rather than transparency — a self-contained square icon needs its own background to stay legible regardless of the browser chrome's own light/dark state. Multi-resolution (16/32/48/64/128/256px) via Pillow's ICO writer. **This predates the navy repaint below and still uses the old `#120d0c` background** — regenerating it (and the logo file itself) is tracked separately; see "Known gaps."

## Palette

No theme switch (no user-facing toggle, no `prefers-color-scheme`) — but the page is no longer one flat color either. Header/nav chrome, the hero, Visit (with the map), every overlay/modal, and the footer stay the original dark navy surface; Story, the Full Menu, and the Gallery teaser are light surfaces (cream/white) that alternate so no two neighboring sections share a look. Every color still traces back to a small set of tokens — change a color by changing the token, not by hunting down individual rules — there are just two places tokens get defined now instead of one.

### Dark surface (the default — `:root`)

- `--bg` (`#161b28`, slate navy) / `--bg-alt` (`#1f2636`, alternate sections and cards) / `--ink` (`#e8e0d0`, soft cream text) / `--accent` (`#c29a6b`, dusty brass — text, prices, active tab, nav pill fill, focus rings, the map pin) / `--accent-fill` (what a filled accent surface actually paints — `.btn-primary`'s background; equal to `--accent` here, see the light surfaces below for why they're separate tokens) / `--on-accent` (`#161b28`, text sitting on an accent-filled background). This is a deliberately muted second pass on the original navy + amber-wood scheme — same roles, lower saturation and a cooler, calmer bg — after the first version read too vibrant.
- Derived from those via `color-mix()`, not written out as their own literals, so a future edit to the leaf tokens above propagates automatically: `--accent-deep` (accent-fill mixed ~55% toward black — the primary button's/FAB's thin contact shadow and the active tab's contact shadow), `--line` (ink at ~12% — hairline borders), `--muted` (ink at ~60% mixed against a fixed warm charcoal rather than transparent — secondary text; blending against transparent let the cool `--bg` show through and read faintly blue, so it's pinned to a neutral/warm grey instead). A fair amount of the file still writes `color-mix(in srgb, var(--ink) N%, transparent)` inline at its own bespoke percentage rather than reusing `--line` — that's deliberate variety for a specific hover/active weight a component wants, not an oversight.
- `--surface`/`--surface-edge` (raised chrome — ghost buttons, tabs, the floating nav — and that chrome's own contact-shadow edge), `--glass` (translucent navy backdrop for the nav pill/mobile topbar — `color-mix(in srgb, var(--bg) 65%, transparent)`, so it can't drift out of sync with `--bg` the way a hardcoded `rgba()` copy once did), `--footer-bg`, `--card-shadow` (navy-black, not brown-black or flat black, so every drop shadow reads as "further into this navy room's own shadow").
- `--navy` (`#161b28`) is the one token that's a plain fixed constant, never redefined on a light surface — see the light-surfaces section below for what it's for.
- `color-scheme: dark` on `:root` is what gets native form controls (the event modal's date input, scrollbars) to render dark instead of the browser's light default.
- Contrast (WCAG relative-luminance formula): ink/bg ≈ 13.1:1, accent/bg ≈ 6.65:1, on-accent/accent-fill ≈ 6.65:1.

There used to be a second, light-mode block here (`:root[data-theme="light"]`), a toggle button (`components/themeToggle.js`), and matching `data-theme`/`prefers-color-scheme`/`localStorage` logic in `script.js` and an inline pre-paint script in `index.html`'s `<head>`. All of that is gone — removing it is what let every "theme-aware" rule elsewhere in `style.css` collapse from a dark/light pair down to one value, before the light surfaces below existed. `script.js` does call `localStorage.removeItem("klandestina-theme")` once on load, purely so a returning visitor who'd previously picked light mode doesn't keep carrying that now-meaningless stored value around forever.

### Light surfaces — `.surface-light` (cream) / `.surface-white` (white)

Applied directly to a `<section>` in `index.html` — `#story`/`#gallery` get `.surface-light`, `#menu` gets `.surface-white` (`fi/index.html` carries the same classes, since `scripts/prerender.mjs` generates it from `index.html` — see "Finnish URL"). Nothing else changes surface: the hero, Visit (`.section-ambient`, unchanged), the footer, and every overlay/modal (gallery overlay, lightbox, dish/item modal, event modal, mobile nav overlay) all live outside any `.surface-light`/`.surface-white` DOM subtree, so they keep rendering with `:root`'s dark tokens automatically, with zero extra CSS — confirmed directly (computed `background-color` of `.gallery-overlay`/`.item-modal-overlay` opened from a light section is still `rgb(22, 27, 40)`).

- `--ink: #161b28` / `--accent: #8c6030` (a darker brass than the dark surface's own `#c29a6b` — that lighter brass doesn't carry enough contrast against cream/white) / `--accent-fill: #8c6030` / `--on-accent: #f6f1e7` (one fixed cream value on *both* classes, not whichever of `--bg`/`--bg-alt` — it's chosen for contrast against the brass fill specifically, which is identical either way) / `--muted: #575b68` (a literal, not the dark surface's warm-charcoal formula — that formula was tuned for blending with a *cream* ink; reusing it with a navy ink here gives nonsense). `.surface-light` sets `--bg: #f6f1e7` / `--bg-alt: #ffffff`; `.surface-white` is the same pair swapped.
- `--card-shadow` becomes a soft navy-tinted shadow (`rgba(22, 27, 40, 0.09)`) instead of the dark surfaces' near-black one — strong enough to lift the gallery teaser's tiles off the page, not a heavy dark halo.
- **Every derived token is restated here too**, not just the leaf ones — `--accent-deep`/`--line`/`--surface`/`--surface-edge`/`--glass`/`--footer-bg` all get their own copy of the same formula `:root` uses. This isn't redundant: a custom property's `var()` references resolve using the scope where *that property itself* is declared, not the scope where it's eventually used — `:root`'s own `--surface-edge: color-mix(in srgb, var(--bg-alt) 55%, black)` keeps using `:root`'s `--bg-alt` for every element on the page, including ones inside `.surface-light`, unless `.surface-light` declares its *own* `--surface-edge`. Confirmed the hard way: the first version only restated the leaf tokens, and the gallery teaser's tiles rendered navy instead of soft grey until every derived token got its own copy too.
- `--navy` (`#161b28`, fixed, defined once in `:root`, never redefined here) is for the handful of things that need to stay navy regardless of which surface they're on: the dish-card photo-caption scrim (`.visual .scrim` — darkens toward `--navy`, not the scoped `--bg`, so caption text stays legible even if a dish card ever ends up on a light surface) and the Full Menu's active category pill (see below).
- **Menu category pills** get their own override, not pure token substitution: inactive is transparent with a `--line` border and `--ink` text; active is a solid `--navy` fill with cream text — not brass, even though brass is this surface's own accent-fill. Brass is already the surface's text/price/eyebrow color; a brass-filled active pill sitting next to brass prices would blur together, where navy reads as a clear, deliberate "selected" signal. This only touches the Full Menu's own sticky tabs — the gallery overlay reuses the same `.tab`/`.tab.active` markup for its own album pills, but that overlay always stays dark and is never a descendant of `.surface-light`/`.surface-white`, so it's unaffected.
- **Buttons**: `.btn-primary` already paints `var(--accent-fill)` (brass here) with `var(--on-accent)` text and the same flat 2px contact shadow as the dark surface — no override needed. `.btn-ghost` gets one: transparent background (the dark surface's filled `var(--surface)` would be a near-white block on an already white/cream page) and a stronger `ink` ~25% border (vs. `--line`'s own ~12%) so the outline stays visible with nothing behind it; hover already turns the border to `var(--accent)` via the shared rule.
- **Ambient glow**: none. `.surface-light`/`.surface-white` paint an opaque `background: var(--bg)` on the section itself, which is what blocks `body::before`'s fixed, page-wide glow from showing through (see "Global ambient background" below) — no extra rule needed for that part. The one glow that lived *inside* a now-light section on its own terms, `.menu-photo-ambient`'s fallback (shown only when a menu category has no on-theme photo), got its own opacity dropped from 9–11% to 3–4% directly, since that's a fixed literal, not something the surface swap touches automatically.
- **Contrast** (WCAG relative-luminance formula, verified by calculation against the exact values above): ink/cream ≈ 15.3:1, ink/white ≈ 17.2:1, muted/cream ≈ 6.0:1, muted/white ≈ 6.8:1, accent/cream ≈ 4.9:1, accent/white ≈ 5.5:1, on-accent(cream)/accent-fill ≈ 4.9:1 — all ≥4.5:1. Re-checked Lighthouse (mobile) after the change: Accessibility held at 93 (same as before), SEO 100, Best Practices 96. One concrete regression surfaced and got fixed in the same pass: `.menu-item-desc`/`.menu-item-tag`/`.menu-empty`/`.price-label`'s own bespoke ink-alpha blends (45–55%, tuned for the old dark Menu background) dropped to ~3.2–3.9:1 against white — under `.surface-light`/`.surface-white`, all four now use `var(--muted)` instead (a scoped override, since `.menu-item-tag`/`.price-label` are also reused — unaffected — inside the item detail modal, which stays dark).

**Global ambient background.** A flat `var(--bg)` on `body` reads as harshly flat next to a soft ambient glow. `body::before` (in `style.css`) layers four large, very soft `radial-gradient` blobs built from `color-mix(in srgb, var(--accent) N%, transparent)`, plus one cooler blob (a fixed `rgba(42, 51, 80, 0.3)` — lighter slate, not derived from a token) low and to the right, so it reads as ambient light with some depth/dimension to it rather than one uniform warm spotlight — the same technique `.hero`/`.section-ambient` already use locally, just pulled up to the `body` level so it's the shared baseline everywhere instead of being invented per-section. Every one of these accent glows is capped to roughly 8–12% on dark surfaces — the original version ran as high as 20% in a couple of spots, which is part of what read as "too vibrant"; nothing should glow orange. `position: fixed` (not `absolute`) anchors it to the viewport rather than the document, so scrolling a very tall page doesn't carry it miles off-screen — it stays put like ambient light in a room. `z-index: -1` plus `pointer-events: none` keep it strictly decorative; sections that already set their own opaque background — `.hero`, `.section-ambient` (Visit), and now `.surface-light`/`.surface-white` (Story, Menu, Gallery) — simply paint over it locally, which is fine; Dishes and the footer are the only two sections left relying on it directly.

**Gradient scrims under photo captions** (dish cards) darken toward `var(--navy)` — a fixed token, not the scoped `--bg` — specifically so they stay legible regardless of which surface the card sits on (the Dishes section itself is still dark today, so this has no visible effect yet, but the token is correct either way). The item detail modal's close-button background keeps using `color-mix(in srgb, var(--bg) 55%, transparent)` instead — that one's fine as-is, since the modal it's in never leaves the dark `:root` scope to begin with.

## SEO

The site is set up for `https://klande.fi/` (root domain, no subfolder — see the `CNAME` file at the repo root). Everything here traces back to real content already in the repo (`data/site.json`, `data/i18n/`) — nothing here is invented copy.

- **`<title>` / meta description / canonical.** `index.html`'s `<title>` and `<meta name="description">` mirror `data/i18n/en.json`'s `seo.title`/`seo.description` keys (kept as plain data so `fi/index.html` can pull its own copy from `fi.json`'s matching keys — see "Finnish URL" below; `fi.json`'s pair is machine-translated, like the rest of its strings, and needs native review before launch). `<link rel="canonical">` points at `https://klande.fi/`.
- **Open Graph / Twitter Card** tags use the same title/description, `og:url`/`og:image` as absolute `https://klande.fi/...` URLs (required for OG — a relative path doesn't resolve correctly when a crawler fetches it out of page context), `og:locale` `en_US` with `fi_FI` as the alternate, and `twitter:card` `summary_large_image`.
- **`images/og/og.jpg`** (1200×630, ~48KB) is a crop of the hero photo (`images/hero/hero-desktop-source.png`, see "Hero photo") centered on the neon sign and kitchen window — real photography of the restaurant, not a generated logo-on-gradient graphic (an earlier version was the latter; replaced once a real hero photo existed to crop from instead). One-off (`sharp(...).extract({...}).resize(1200, 630)`, same quality/sharp pattern as the rest of the site's image tooling), not wired into a build step — regenerate it by hand (same crop box, or a new one) if the hero photo ever changes.
- **JSON-LD** (`index.html`, a static `<script type="application/ld+json">`, not rendered by `script.js` — so it's present even with JS disabled; `fi/index.html` carries the identical block, since it describes the one restaurant, not a specific page — see "Finnish URL") describes the site as a schema.org `Restaurant`: name, url, image, email, `telephone` (`+358413299494`, the structured-data form — no spaces — from `data/site.json`'s `phone.link`/`phone.display` pair, which also feeds every visible `tel:` link on the site), address (`PostalAddress`, street + locality only — see below), geo (from `site.json`'s `coordinates`), `openingHoursSpecification` (parsed from `site.json`'s `hours` display strings into structured day/time ranges — Friday/Saturday's "17:00–24:00" is written as `closes: "23:59"`, the more broadly-compatible way structured-data consumers expect a midnight close, rather than the literal "24:00"), `servesCuisine: "Mexican"`, `hasMenu` pointing at `https://klande.fi/#menu`, and `sameAs` (the three social links from `site.json`). **`priceRange` is still omitted** — `data/site.json` has no such field, and per this task's own rule, a missing fact gets left out rather than guessed. Same for the address: no postal code or `addressCountry` is in `site.json`'s plain `address` string, so `PostalAddress` only carries `streetAddress`/`addressLocality`. **This block is hand-written, not generated — if hours, address, or contact details in `data/site.json` change, this JSON-LD needs a matching manual edit, nothing keeps the two in sync automatically.** (A second, *generated* JSON-LD block — one schema.org `Event` per currently-upcoming entry in `data/events.json` — is written separately by `scripts/prerender.mjs`; see "Events" above.)
- **`robots.txt`** allows everything (`Allow: /`, no disallow lines — `/images` and `/data` are both crawlable) and points at `sitemap.xml`. **`sitemap.xml`** lists both `/` and `/fi/`, each with `hreflang` alternates; see "Finnish URL" below.
- **Favicon**: `favicon.ico` exists and is linked (`/favicon.ico`), but see the Palette section's "Known gaps" — its background still predates the navy repaint. **No `apple-touch-icon` exists in the repo** — rather than generating one from the logo unasked, this is flagged here instead; a 180×180 PNG (ideally on the same navy background the favicon should use) would need to be added and linked (`<link rel="apple-touch-icon" href="/apple-touch-icon.png">`) separately.

### Prerendered menu + contact content

The menu and the address/hours/email/phone block are both rendered entirely by `script.js` — fine for a browser, but it means the raw HTML response (what a non-JS crawler or a quick text fetch sees) has neither. `scripts/prerender.mjs` (plain Node, no dependencies) fixes that: it reads `data/menu.json`, `data/site.json`, and `data/i18n/en.json`, and writes static English HTML between two marker-comment pairs already sitting in `index.html` — `<!-- PRERENDER:MENU:START/END -->` inside `#menu-list`, `<!-- PRERENDER:CONTACT:START/END -->` inside `#footer-mount`. The menu block is **every category flattened in sequence** (not tab-separated — there are no tabs in the static version), including Drinks' four sub-groups, every item's name/description/price/allergen codes, and a thumbnail (with real `width`/`height`, via `components/dishImageDims.js`) wherever the item has one.

Both target containers were already fully overwritten by existing JS the moment it runs — `renderMenuCategory()` does `menuList.innerHTML = ""` before rendering just the active tab, `renderFooter()` does `container.innerHTML = `<footer>...``. Neither needed a code change for that to clear the prerendered content; they already behaved this way. In practice that means a brief flash of the full static menu/contact block before `script.js`'s `fetch()` calls resolve and it collapses to the normal tabbed view/real footer — verified with Playwright that JS-disabled shows all 40 menu items + full contact info, and JS-enabled settles to exactly the same single-category view (5 Lunch items) and real `<footer>` as before this existed, with zero leftover prerendered nodes.

Run it after editing `data/menu.json`, `data/site.json`, or `data/i18n/en.json`: `node scripts/prerender.mjs`. `.github/workflows/prerender.yml` also runs it automatically on a push touching those files (plus `data/i18n/fi.json`, for the Finnish page — see "Finnish URL" below), commits the result as `github-actions[bot]` only if something changed, and requests a Pages rebuild, the same shape as `.github/workflows/gallery.yml`. **If you edit `index.html`'s surrounding markup by hand** (not the data files), re-run the workflow manually (`workflow_dispatch`) afterward — the trigger only watches the data files, since a markup-only edit doesn't change what the script would generate anyway, except around the markers themselves.

## Finnish URL

Finnish searches find a Finnish page at `https://klande.fi/fi/`, not a client-side text swap on top of the English one. `/fi/index.html` is generated from `index.html` by `scripts/prerender.mjs` (`node scripts/prerender.mjs` runs both in one call — see "SEO" above), so the two never drift apart by hand-editing one and forgetting the other.

**What differs between the two files, generated on every run:**
- `<html lang>` (`en` / `fi`), `<title>`/meta description, `<link rel="canonical">`, `og:url`, `og:locale` (+ `og:locale:alternate` swapped), and `twitter:title`/`twitter:description` — all from `data/i18n/{en,fi}.json`'s `seo.title`/`seo.description`. `og:image` and the JSON-LD block are **not** touched — both describe the one restaurant, not "this page", so they stay identical and keep pointing at the canonical root on both files.
- Every statically-written `data-i18n="path">Text<` element in the page's own markup (hero headline, every section's eyebrow, Story's full copy, "Get Directions", etc.) — swapped to the matching string from the right language file via a simple `data-i18n="path">...</` pattern match, not a DOM parser (see the script's own comments for why that's safe here: every one of these today has `data-i18n` as the tag's last attribute with plain, unnested text after it).
- The `PRERENDER:MENU`/`PRERENDER:CONTACT`/`PRERENDER:EVENTS`/`PRERENDER:EVENTS_JSONLD` blocks (see "SEO" and "Events" above) — built from the matching language's category labels/notes/item descriptions, or event titles/descriptions, instead of English's. The *set* of upcoming events itself is identical on both pages — only the text differs — since `scripts/prerender.mjs` resolves `data/events.json` once per run, not once per language.

**Both files carry the same three `hreflang` alternate links** (`en` → `/`, `fi` → `/fi/`, `x-default` → `/`) — written once, by hand, into `index.html`'s `<head>`, and copied over unchanged into `fi/index.html` since both pages list the same two URLs either way.

**Starting language is decided by the URL, nothing else.** `script.js`'s `getLanguageFromPath()` reads `window.location.pathname` — `/fi` or `/fi/...` starts Finnish, everything else starts English, on first page load. There's no `localStorage` persistence and no browser-language (`navigator.language`) fallback; the URL is the only source of truth, which is what makes `/` and `/fi/` two genuinely separate, independently indexable pages rather than one page with a remembered state.

### Switching language without a page load

The EN/FI switch (`components/langSwitch.js`, unchanged) hands a language code to `setLanguage()` in `script.js`. That function used to do a real `window.location.href` navigation to `/` or `/fi/`, carrying over `window.location.hash` — **a real bug, not just a rough edge**: `window.location.hash` is only ever set by a literal `#section` anchor click (`components/nav.js`'s pill links are genuine `<a href="#id">`s with no `preventDefault()`), and goes stale the moment the visitor scrolls past that point by any other means, which is most of the time. A full reload to that stale (or entirely absent) hash is exactly what produced the reported symptom — landing "around the Menu section" after toggling from deep in Gallery (a leftover `#menu` from an earlier pill click), or at the top (no hash at all).

`setLanguage()` now swaps every piece of language-dependent state **in place** — no navigation, no reload:

- **Translations** — `applyTranslations()` (unchanged) re-walks every `[data-i18n]`/`-placeholder`/`-aria-label`/`-alt` element, which was already the whole site's chrome-translation mechanism; it just wasn't being re-run on a switch before, since a switch meant a fresh page load that ran it once from scratch anyway.
- **The actually-per-language dynamic sections** — re-rendered individually, each chosen specifically to preserve whatever state the visitor had going rather than reset it:
  - `renderMenuCategory(activeCategoryId)`, not `initMenuTabs()` — rebuilds `#menu-list`'s item descriptions in the new language without touching the tabs row at all, so the active tab and its own horizontal scroll position are simply never disturbed.
  - `renderSignatureDishes(startOffset)` — the dish carousel's auto-scroll loop needs rebuilding too (descriptions are per-language), which used to mean restarting its `requestAnimationFrame` loop at `offset = 0`, snapping the row back to the start. `components/dishCarousel.js`'s `renderDishCarousel()` now takes an optional `startOffset` and returns `{ getOffset }`; `script.js` reads the running carousel's current offset out before rebuilding it and hands it back in, so the loop continues rather than visibly resetting.
  - `renderEvents()` re-resolves event text/ordering inside the stable `#events-grid` container.
  - `refreshGalleryMosaicLabels()`/`refreshGalleryOverlayLabels()` (`components/galleryMosaic.js`/`galleryOverlay.js`) update just the gallery's own chrome text in place, without rebuilding the masonry grid — these already existed, written for exactly this, but were dead code (imported, never called) until now, since switching used to mean a full reload that made them unnecessary.
- **`<title>`/meta description/canonical/`og:*`/`twitter:*`** — `updateHeadForLanguage()` swaps the same set `scripts/prerender.mjs`'s `localizeHead()` swaps for the static `fi/index.html` build at prerender time, just done live for the already-loaded page. `og:image` and the JSON-LD block stay untouched, same reasoning as prerender time: both describe the one restaurant, not "this page".
- **The URL** — `history.replaceState(history.state, "", "/fi/" + hash)` (or `"/"`), not `pushState` and not a navigation. `/fi/` stays the real, shareable, crawlable address (confirmed: reloading after a switch, or opening the resulting URL fresh, serves the real prerendered `fi/index.html`, independent of any JS state) without a page load, and `replaceState` means the switch itself never shows up as its own entry in browser history — simplest way to guarantee the back button can't get "stuck" on one: there's nothing to get stuck on.

**Scroll position is preserved by explicit anchor-tracking, not left to chance.** Before any of the above runs, `captureScrollAnchor()` samples a point near the top of the viewport (`document.elementFromPoint`, stepping down past any `position: fixed`/`sticky` chrome it lands on — the shortcut nav, the mobile topbar, and the sticky menu-tabs bar all needed explicitly excluding, since their own screen position doesn't move when content above them reflows and anchoring to one would silently produce a no-op correction) and records that element plus every one of its ancestors up to `<body>`, each with its own pre-swap `getBoundingClientRect().top`. After the swap, `restoreScrollAnchor()` walks that chain front-to-back for the first node still actually in the document (the deepest hit is often exactly what gets replaced — e.g. a single `.menu-item` inside a re-rendered `#menu-list` — which is why the whole ancestor chain is kept, not just the one hit) and scrolls by exactly how far *that* element's own top moved, correcting for reflow (longer/shorter Finnish text, a menu category re-rendering with different line counts) regardless of how large it turns out to be, without needing to know its size in advance. Forced to `scroll-behavior: auto` for that one correction (`html`'s site-wide `scroll-behavior: smooth` would otherwise visibly animate exactly the jump this is for avoiding) and `overflow-anchor: none` on `html` (so the browser's own native scroll anchoring — which watches for the exact same "content shifted above the viewport" condition — can't also kick in afterward and double-correct on top of it).

Verified end to end with Playwright, not just reasoned through: toggling at six content positions (top, Story, Menu with the Drinks tab selected and scrolled, Events, Gallery, Visit/footer) × two viewports (375×812, 1440×900) stayed within 0-165px of raw `scrollY` drift each way — all of it legitimate reflow compensation (Finnish words are generally longer), confirmed by comparing actual before/after screenshots pixel-by-pixel rather than trusting the number alone: the same menu items, same active ("Juomat"/Drinks) tab, same event card, landed in the same place on screen, just correctly retranslated. Also checked: the back button doesn't add a history entry for the toggle (confirmed `history.length` unchanged); a direct visit to `/fi/` and to `/fi/#menu` both still work exactly as before (this fix only touches the toggle's own code path, not the initial-load one); reloading immediately after toggling lands on the real prerendered `/fi/` page; `hreflang` tags and `sitemap.xml` are untouched (nothing in this fix writes to either).

**One UI state intentionally not specially handled: the event/inquiry modal or the mobile hamburger overlay being open.** Both already sit at a higher `z-index` (100 and 95 respectively) than the language switch (desktop `--shortcut-nav`/`.utility-bar` and the mobile topbar's own switch, both well under that), which **already** makes the toggle physically unreachable by a real click while either is open — not a gap this fix introduces. `setLanguage()` is still safe if it ever runs while the event/item modal is open regardless (confirmed): it never touches modal visibility, DOM, or form field values, only elements tagged `data-i18n*` for text, so an open modal's state (including typed-but-unsubmitted form values and focus) survives untouched by construction. The mobile nav overlay — reachable in principle since it's the switch's own container that's sometimes behind it — is explicitly closed (`mobileNavHandle.close()`, exposed from `renderMobileNav()`'s return value) after the swap, with no scroll side effect of its own (only a link click inside it triggers a scroll, via a separate `onDone` callback this close path doesn't use).

`sitemap.xml` lists both URLs, each with all three `hreflang` alternates via `xhtml:link` (the sitemap-alternates convention search engines expect, separate from the per-page `<link rel="alternate">` tags above).

**`.github/workflows/prerender.yml`** now also watches `data/i18n/fi.json` and commits `fi/index.html` alongside `index.html` whenever either changes — see "SEO" above for the rest of that workflow's shape. If you ever edit `fi/index.html` (or `index.html`) by hand instead of through the script, re-run `node scripts/prerender.mjs` (or dispatch the workflow) afterward — a hand-edit to one file doesn't propagate to the other on its own.
